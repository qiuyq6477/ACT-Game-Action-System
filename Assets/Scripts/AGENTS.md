# Assets/Scripts 模块指南

动作系统的逻辑与表现代码：`Character/`（角色、动作控制器、判定盒）、`Methods/`（表数据里的脚本函数表）、`GameMain.cs`。

## 热路径（每帧执行的代码）

- 每帧路径**禁止**堆分配：不许出现 `new` 数组 / `List` / 字典字面量、`string` 拼接、值类型装箱。每逻辑帧往里 `Add` 的常驻 `List`（输入记录、预约动作、本帧激活的盒信息）**必须在字段初始化时就按满员容量 `new List<T>(n)` 备好**：一个平时不用那条路径的角色（AI 接管之前的敌兵就是这样）第一次开始登记时会连着扩容好几次，而那些字节全落在战斗那一拍上。表里的字符串一律在 `GameData.Load()` 里烘焙成数值之后再用（例：`ActionInfo.rootMotionParam`、`AttackBoxTurnOnInfo.tagMask`）。往 `ActionInfo` 及其阶段结构体里加"运行期算出来的"字段时，必须标 `[NonSerialized]` 并在 `GameData.Load()` 里赋值：`Resources/GameData/Action.json` 是策划表，不往里塞派生字段。
- `foreach` 遍历结构体数组拿到的是拷贝，改它的成员会直接编译不过（CS1654）：改表数据就先 `ActionInfo info = source;` 拷一份再改，改数组元素（数组本身是引用）就用带索引的 `for`。**同一条坑在 `List<struct>` 上编译器不报错**：`HitRecords[i].Tick()` 改的是一份拷贝，改了等于没改，所以 `HitRecord`、`ForceMove` 这类结构体的倒数/推进一律走"取出来 → 改 → 写回去"三步（带索引的 `for`，见 `CharacterObj.Tick` 与 `AddHitRecord`）。

## 碰撞盒标签与命中采样

- 只有 `BoxTagRegistry` 允许认识标签字符串，新增标签一律走 `MaskOf`；判定处只许位与 `(a & b) != 0`，不许再比字符串。标签总数上限 31，超了 `MaskOf` 报错并返回 0（该标签从此判定不到），加标签时看 Console。标签的位号按注册先后分配，**同一次运行内稳定、跨运行会变**（各 prefab 的 Awake 顺序不固定）：日志和断言里只打标签名，别把掩码数字当常量。
- 盒子组件的绑定（认主人、烘焙 `TagMask`、认领碰撞体、建好每拍重填的接触列表）全在 `CharacterObj.BindBoxes()` 里，`Awake` 只调它：**EditMode 下 `Instantiate`/`AddComponent` 都不触发 `Awake`**，用例要直接叫它（`BindBoxes`、`CueReceiver.Init` 都是这么设计的）。绑定必须早于第一个逻辑帧。
- 命中相交给逻辑帧主动采样（`GameMain.TickAll` 的相交采样拍 → `CharacterObj.SampleOverlaps` → `AttackHitBox.SampleTouches`），**不许**再写 `OnTriggerEnter/Exit`：物理回调按 `Fixed Timestep 0.02`（50Hz）触发，与 60Hz 的逻辑帧错频，窄窗口静默打空、大位移直接穿过（`Doc/plan/beatemup-port.md` 切片 1.3）。
- 相交查询只认 `BeHitBox` 层（`BeHitBox.QueryMask`），受击盒必须归到这一层，否则采不到；地面与道具因此天然被排除在缓冲区之外。
- "这一拍谁打到了谁"的真入口是静态的 `CombatPipeline.DealWithAttacks(all, player)`（`GameMain.DoAttack`→`DealWithAttacks` 整段都在里面），它只做两件事：查"打到谁"（`CanAttackTargetNow` + `CanHitTargetAgain`）和把结果交给 `ResolveHit`。**用例只准打真入口，不许再照抄生产行**（以前 DoAttack 是私有的，第16区就照抄了一份，抄漏一行就测不到那一行）。配对的结构是"玩家↔每一个敌兵"两条循环，**阵营因此是隐含在循环形状里的**；要让一记攻击打自己人（被摔出去的身体砸队友），必须在 `AttackInfo` 上写 `hitOwnSideOnly`——那两条常规循环见到它就跳过，只由末尾那条同侧相碰认领，而相碰只对 `CharacterObj.HasOwnSideAttackOpen()` 为真的人做二次方循环（缺省 false = 老行为，二十几个敌兵也不会变成几百次查询）。
- 数值结算是**可选件**，而且"没装"必须等于"老行为"而不是"新行为"：没挂 `CombatStats` 就一滴血不掉、打断/硬直/击退与 1.9 之前一字不差；`PoiseGauge.maxPoise` 留 0 或攻击那行的 `poiseDamage` 留 0 都算"没有霸体，一律打断"（缺省站在老行为那一边，漏填才不至于做出"谁都打不动他"这种查不出来的坑）。格挡的开关做在**受击阶段**上（`BeHitBoxTurnOnInfo.block`，因为这一条本来就在回答"这一部分防御是什么防御"），而"打在背后不算挡住"由几何判（`CharacterObj.FacesToward`），表里不必再多一个会填错的方向；挡住之后走的是攻击方表上的 `blockStunFrames`/`blockPush`，动作一动不动、只冻时钟。致死那一记按 **catalog `Death`** 路由到这个人自己那份子集里的行，所以 `PickActionMethod` 认不出正反手 id 时必须落到 `candidates[0]`（移植家的受击就只有 `PlayerHit` 一行）——返回空 `ActionInfo` 等于"挨了一拳站在原地不动"。
- 盒子「在哪」和帧事件同样是表数据，不许留回动画：`attackPhase[].track` 是稀疏关键帧，`GameData.Load` 摊平成按帧号直取的 `bakedPosition/bakedSize`，只有盒子开着的那一拍才写 `localPosition` + `BoxCollider.size`（写局部坐标，面向镜像因此自动生效；没填 track 就一个数都不碰）；`ActionInfo.cues` 由 `ActionController.CalculateCues` 按**游标**派发而不是区间比较（循环回绕那一拍区间是倒的，点会被整段跳过），换动作置 `startFrame-1`、回绕置 `-1`，硬直期间不响。派发口是 `CueDispatch.Handler(owner, info, cue)`（只允许一个消费者，owner 是"这一拍响的这条 cue 属于谁"，特效要摆在他脚下），消费者是 `Presentation/CueReceiver`：音效只有一台常驻 `AudioSource` 靠 `PlayOneShot` 叠放，特效**按名字建池**（`EffectCapacity` 个实例开机摆好，放一次只是 SetActive+Play，超了就回头复用第 0 槽），收回时机是 `LogicClock.Frame + lifeFrames`，由 `TickAll` 最后一拍 `CueReceiver.Tick` 过一遍。源工程那种"每响一次 Instantiate 一个"照搬进来就是每记一次命中一次分配。**预热扫的是全表**（用到才载会把一次磁盘 IO 塞进打击那一拍），所以表里 cue 的 `param` 必须能在 `Resources/BeatEmUp/{Audio,Effects}` 里取到——第18区 `EveryCueNameInTheTableHasItsAsset` 钉的就是这条，缺素材在开机前就红，而不是等验收时"怎么没有挥空声"。两者的拍号与窗口 `min` 同一个基准（0-based 恒等）。

## 逻辑时钟与单位

- 逻辑层的"时长"一律是 `int` 逻辑帧（`durationFrames`、`freezeFrames`、`hitStunFrames`、`inFrames`、`validInFrames`、`CooldownFrames`…），不许再出现按秒累加的字段。动作内部的窗口存**绝对帧号**（`FrameRange`），判定只剩整数比较。
- 一个动作的时长真源只有表里的 `durationFrames`：窗口上界、RootMotion 的线性段、CrossFade 的 offset 全以它为标尺。**唯一的例外**是"举着人"这类既不摆盒子也不响 cue 的状态行（`PlayerHold`、`Grabbed` 填 180 拍 = 3 秒）：它表达的是"这个状态最多待多久"，Animator 里那条 12 帧的片子放完就停在末帧上（clip 的 `m_LoopTime` 是 0）；带了 `track` 或 `cues` 的行不许这么填，拍号会对不上。美术重导 clip 之后这个数必须跟着改——跑菜单 `Tools/ACT/打印动作时长` 校对（跟实际长度对不上打 ✗，顺带查空窗口和越界窗口）。从 `.anim` 曲线迁帧数据同样**不许手数**：跑 `Tools/ACT/导出 BeatEmUp 帧数据草稿`（产出 `Doc/plan/beatemup-anim-dump.md`），换算公式 `min = 抬起帧`、`max = 落下帧 − 2`（第 n 拍摆的就是 clip 第 n 帧，是恒等映射；窗口按跨帧语义生效 min..max+1），推导写在工具头注释里；工具同时产出可以直接粘的 `track`（位置/尺寸已按帧合并，尺寸 = 缩放曲线 × 精灵 size）与 `cues`（`kind` 是 `CueKind` 的序号）两段 JSON。
- 派生候选**同分时的赢家是表里靠前的那一行**（`Tick` 里的冒泡只比大小、不比谁先），所以 `priority` 不许留空当装饰：攻击/跳跃/格挡这类"真的要出招"的行必须高于移动行的自取消（本工程用 攻击 10 / 倒地追击 20 / 移动 0）。**站立这类兜底行不许挂 `cancelTag`**——挂了等于"每个没按方向的拍都自己挤自己一次"，而它通常是表里第一条，于是同键的攻击永远出不来（demo 的 `BoxingStand` 从来不挂 tag，道理相同）。
- 跳跃是**一对**参数：`ActionInfo.jumpUpSpeed`（换动作那一拍交给 `CharacterObj.Jump` 的初速度，米/秒）和 `CharacterObj.weight`（每逻辑帧加到下落速度上的量）——滞空拍数 ≈ 2·v0/(weight·60)、最高点 = v0²·60/(2·weight)，所以改一个必须看另一个。飞行与落地**不走 root motion**：`.anim` 里那条 y 曲线不认识地面。落地那一拍由 `landActionId` 切动作（`CharacterObj.JustLanded` 在移动拍里写、动作拍在它之后，所以差一拍），`autoNextActionId` 只管"片子先走完"的那一半，两者都要填。
- 抓取是**位置约束**不是父子挂接：`AttackInfo.holdFrames`（>0 才抓人，也是撒手的拍数）+ `holdOffset`（相对举人者脚底，x 身前 / y 高度 / z 车道）在命中那一拍交给 `CharacterObj.TryGrab`，此后每拍由 `ApplyHolds` 重算被举者的坐标（源工程是进状态时摆一次，玩家一动敌人就飘在原地）。被举者的 `Move()` 整拍跳过、同轨推挤跳过他，否则地面探测会把他 snap 回地面、推挤会把他推离手边。**撒手的时机写在动作上**：`ActionInfo.keepHold` 为 true 的行（举着人打的这几招）之间换动作算"仍然举着"，换到一个没写它的行（受击、投掷出手）就撒手；被举者自己换了动作同样撒手（`beCancelledTag` 留空钉死他那行，而攻击方的 `targetActionChange` 走预约列表不受它管）；`holdFrames` 走完是兜底。偏移的 x 随 `Inversed` 取负、z 永不取负（跟纵深同一条法则）。**投掷不是一段专门的代码，就是一记打在手里那个人身上的攻击**（`PlayerThrow` 的合成盒摆位 = `holdOffset`，尺寸要罩得住他）：解约束之后要做的事（换动作、按 `ForceMoveMethod` 的 `Arc` 抛物线飞、进命中记录）全在 `CombatPipeline.ResolveHit` 里，另写一遍就是重复实现。**"被摔"与"被打退"要分成两行动作**（源工程 `hitOtherEnemiesWhenThrown` 开、`hitOtherEnemiesWhenFalling` 关），而区分它们的必须是投掷那记 `targetActionChange` 按 id 指名的一行（`EnemyThrown`）——运行期再记一个状态就是第二个真源；要砸队友就在那一行开一记 `hitOwnSideOnly` 的攻击。
- `Time.deltaTime` 只准在 `GameMain.Update` 里读一次，"该跑几个逻辑帧"的换算归 `LogicClock.TicksDue`。`LogicClock.Tick` 全工程只准用两处——把"米/秒"的速率换算成每帧位移、以及步进 Animator。速率（`moveSpeed`、`weight`）仍然带秒量纲。
- Animator 是从属：`ActionController.Awake` 里 `anim.enabled = false`，只在时钟推进的那一拍被 `anim.Update(LogicClock.Tick)` 步进，硬直时两者一起不前进。**但换动作/循环那一 tick 必须额外补一次 `anim.Update(0f)`**（0 步长只求值不推时间）——否则顿挫期间根本摆不出新姿势，受击动作要等整个 hitStun 走完才露出来，打击感就这么丢掉（见 `Doc/plan/refactor.md` 的 Phase 2 实施记录）。不许再读 `GetCurrentAnimatorStateInfo` 之类的动画进度当逻辑真源，也不许再用 `anim.speed`。
- 角色控制器的铁律：**`animKey` == Animator 状态名 == clip 文件名**，三者同名才对得上（`打印动作时长` 就是按状态名查的），状态之间零转换——切哪个状态、从第几拍开始全由 `ActionController` 决定。精灵玩家的控制器由 `Tools/ACT/生成 BeatEmUp 玩家的 AnimatorController` 从表生成，**派生资产建完必须重新读盘数一遍状态**：`new AnimatorController()` + `AddLayer` + `CreateAsset` 吹出来的层是空壳（`m_StateMachine: {fileID: 0}`），日志报"建了 21 个"而盘上什么都没有。用 `AnimatorController.CreateAnimatorControllerAtPath` 才有真状态机。**表里每加一条新的 `animKey`，就要重跑一次这个菜单**：状态不存在时 `CrossFade` 不报错，只在 Animator 里留一条 `GotoState: State could not be found`，表现就是"招式出了、姿势还停在上一张片子上"。
- 判定盒/武器挂点的节点名**必须避开 clip 里已有的绑定路径**（源工程是 `HitBox`、`WeaponPos`）：clip 里那 34 条 `HitBox` 的 `m_IsActive`/位置/缩放曲线现在全归招式表管，节点重名等于让 Animator 和表抢同一个方向盘（移植的盒子因此叫 `BeatHitBox`）。反过来，`SpriteRenderer` 必须和 `Animator` 挂在同一个物体上——clip 的 `m_Sprite` 曲线绑定路径是空的。
- 面向与纵深都是"逻辑一个布尔 + 表现各自落地"：面向的真源是 `InputToCommand.inversed`（输入镜像、位移符号、受力翻转三处都只用它），落地交给角色身上的 `FacingApply`——3D 模型绕 Y 转 90/270，贴在 3D 平面上的精灵只能翻 `localScale.x`（绕 Y 转 90° 会侧对镜头），逻辑层**不许**再写 `transform.eulerAngles = …90/270…`。翻 `localScale.x` 有个代价必须一起处理：子节点上的 `BoxCollider` 会因此拿到负的 lossyScale，PhysX 每帧喊一条 `does not support negative scale or size` 并在热路径上分配，所以 `FacingApply` 把**碰撞体那一层**的 x 符号抵消掉（`UnmirrorColliderShapes`；根节点自己跳过，它的 x 符号就是面向本身）。抵消不影响判定：矩形与胶囊都是对称的，符号不改形状，而盒子在身前还是身后由父节点乘 `localPosition` 决定，跟节点自己的缩放无关。纵深（`KeyMap.Up`/`Duck`，屏幕纵向 = 车道远近）是**屏幕空间轴，永不镜像**：`NatureMove` 里横向乘 `Inversed` 符号、纵深项不乘。
- 九个 Tick（`InputToCommand` / `EnemyMind` / `ActionController` / `AttackHitBox` / `BeHitBox` / `CharacterObj` / `CharacterObj.SeparateLanes` / `CharacterObj.ApplyHolds` / `CueReceiver`）**不许**写 Unity 的 `Update()` 回调：由 `GameMain.TickAll()` 按固定顺序调用（输入→AI 决策→动作→判定盒→相交采样→命中结算→计时与移动→同轨推挤→抓取约束→表现回收）。采样与约束那一拍都是静态入口（`CharacterObj.SampleOverlaps` / `ApplyHolds`），不是组件回调，收的是 `GameMain` 那份"全体角色"。约束那一拍排在**表现回收之前**：被举者的坐标要按举人者**这一帧**的最终位置算，而推挤那一拍已经不承认被举着的人；回收那一读的是这一拍派发出去的 cue 的到期时间，先逻辑后表现才不会有"这一拍的 cue 下一拍才进池子"。改成别处调用的顺序就要重新想一遍谁先谁后。
- Unity 的按键状态每渲染帧只能 poll 一次，所以 `SampleRenderFrame()` 在时钟之外、每渲染帧一次；`Tick()` 里的判定全是整数帧号比较。模拟"某一刻按了什么"一律走 `InputToCommand.AddInput`（测试和以后的 AI、回放都从这里进）。
- 敌兵的 AI（`Character/EnemyMind`）**只登记按键，绝不自己写位移**：想靠近就 `AddInput`，出不出招、走多快仍然全由他自己那份 `actionSubset` 说了算（所以给敌兵换招式是填表，不是改 AI）。登记的键是**世界方向**（`Forward` = 世界 +x），因为 `GetKeyInput` 会在比对表里的命令时按 `inversed` 镜像一次——直接存"我正脸朝的方向"会在转身之后变成"背对着人退开"。面向走 `ActionController.TurnTo`（写 `command.inversed` 并立刻落地；只设 `CharacterObj.Inversed` 的话站着不动时模型不会转）。**进攻配额由调用方数好再传进来**（`Tick(busy)`），不许 AI 自己翻 `CharacterObj.Units`：那会把玩家自己那一拳也算成一个名额。**回防也还是登记按键**：看见玩家进入攻击分类的那一拍抽一次 `Dice.Chance(defendChance)`，抽中就替他按满 `defendHoldFrames` 拍 `KeyMap.Block`，挡不挡得住由表里那一行判（同一记只抽一次——每拍都抽会把 30% 摊成"几乎必挡"；源工程那个概率是挨打瞬间抽的，而本工程的格挡是一行动作、要下一拍才生效，所以抽在起手那一刻）。
- 长按语义 = `KeyMap.Block` **每拍登记**（不吃非方向键的 6 拍节流，否则 `IsKeyHeld` 那一拍宽的窗口必然读成松手）+ **换动作不清历史**（`KeepAcrossActionChange` 单独放行，它不是方向键，别去改脏 `IsDirectionInput`）。于是"按住"就是"每拍这条指令都成立"，不需要额外的 hold 状态机。
- 逻辑层的随机**只准**走 `Dice`（种子 `GameMain.randomSeed`，默认常量，所以不改就能复现同一串），**不许** `UnityEngine.Random`（墙钟）或 `System.Random`（算法随运行时版本变），且只能由**逻辑帧**触发——掺进任何时间量，回放和联网校验就废了。
- 改动窗口语义、动作时钟、顿挫、命中采样、盒子轨迹、帧事件、派生门禁、抓取约束或**伤害/霸体/格挡/死亡路由**，必须跑 `Assets/Editor/ActionFrameClockTests.cs`（Test Runner → EditMode）。它钉的是"第几帧判到、第几帧接得上、第几帧打到、第几帧摆到哪、第几拍响哪条、被举者这一拍跟不跟得上、这一记掉不掉血/断不断动作"，这些差的都是 16.7 毫秒的零头或是"挡住了却纹丝不动"这类肉眼根本看不出来的规则。
- **编辑器不可用（卡在播放模式、Safe Mode、或干脆没开）时不许跳过闸门**：把工程 `rsync` 一份（排除 `Library`/`Temp`/`Logs`/`UserSettings`/`.git`）到别处，用批处理模式跑用例：`Unity.app/Contents/MacOS/Unity -batchMode -nographics -projectPath <副本> -runTests -testPlatform EditMode -testResults <xml> -logFile <log>`，退出码 0 才算过。跑一次约一分钟（首次导入慢一些），它跑的是真编辑器、真物理查询、真 Animator，不是编译而已。同理可以用 `-executeMethod` 进 Play 模式量 GcProbe（注意 `-nographics` 下渲染帧率极高，300 个逻辑帧要几万个渲染帧才凑得出来，别按渲染帧数判稳态）。
- 用例里比较"累加出来的位置"和"每拍位移 × 拍数"必须带容差（`1e-6f`）：两种算法天然差 1 ULP，写死精确相等的话编译器一融合乘加就假红。

## 表函数、场上查询与分类索引

- 第四张函数表 `Methods/CancelConditionMethod.cs`：派生在「窗口 + 标签 + 指令」之后再过一道门禁（`StateIs` 地面/空中、`NearbyUnitInCatalog` 近处有谁、`HoldingUnit` 手里有没有人），表里填 `CancelTag.cancelCondition = {method, param}`；**留空 = 没有门禁**，现有表项行为一字不变。函数名写错按**不成立**处理（默认放行等于悄悄拆门禁），参数在 `GameData.Load` 的 `Validate` 里检查，不留到战斗中间让 `float.Parse` 抛。"同一个键在不同状态下出不同招"（空手按 E 是抓取起手、举着人按 E 是投掷）**靠门禁分流，不靠 priority**：两条都是候选时同分取表里靠前的那一行，等于把出哪招交给填表顺序。"有没有人躺着"这类场上查询按 **catalog** 匹配而不按动作 id：玩家躺下是 `PlayerKnockDownGrounded`、敌兵躺下是 `BeatenFromForward`，两行 id 不同而分类同为 `Beaten`，绑 id 等于把门禁绑死在一行的名字上。
- 场上的人由表生成，不在场景里预摆：第二份表 `Resources/GameData/Wave.json`（一关有哪几波、每波有谁、站在哪个 x 与 z、可玩区四个数）+ `WaveTable.Load`（开机一次，校验 prefab 取得到**且挂了 `CombatStats`**——不会死的兵等于这一波永远清不完）+ `WaveManager`（全灭之后隔 `framesBetweenWavesFrames` 拍开下一波）。`WaveManager.spawn` 是注入的委托，生成一个人的全部步骤只在静态真入口 `GameMain.PlaceCharacter` 里（实例化 + 认盒子 + 交子集），**用例与生产打的都是它**；全体遍历用 `GameMain._all`（`List`，第 0 个是玩家），三个静态入口 `SampleOverlaps`/`SeparateLanes`/`ApplyHolds` 收 `IReadOnlyList<CharacterObj>`。表里没填边界就不建 `LevelBounds`（老行为是不夹）。
- 命中那一拍的"说话"三件套都在 `CombatPipeline.ResolveHit` 里发出**请求**：动作/硬直/推开（逻辑）、`HitFlash.Begin`（白闪）、`DamagePopups.Show`（飘字）。白闪**只走 `MaterialPropertyBlock`**——源工程那句 `sr.material = Resources.Load("HitFlashMat")` 每命中都实例化一份材质，而拿"原来的颜色"要读 `Renderer.material`，同样是实例化，所以退回原样的正确做法是 `SetPropertyBlock(null)` 整块清掉。飘字的数字来自**开机烤的一张 0..99 + 「99+」表**（`number.ToString()` 每记命中分配一次，就是 `Doc/issue` 反复关掉的那类），下标 0 是空串：伤害为 0 的一记（格挡）既不闪也不飘。这两样都由 `TickAll` 的表现回收拍计数，时长是拍不是秒；`HitFlash` 组件在 `BindBoxes` 里就挂好——命中那一拍只许改数，不许 `AddComponent`。
- 表现层的 UI 由代码搭，不手写 `.unity` 里的 RectTransform：`HudBar.Build` 一条血条只要 `Image.Type.Filled` + `fillAmount`，`SetValue` **数值没变就不写**（写一次就脏一次 canvas rebuild）。没挂 `CombatStats` 的角色条子是满的——不装组件等于不参与数值，跟结算那边同一条立场。
- 查"场上有谁"只走 `CharacterObj.Units`（注册在 `BindBoxes`、注销在 `OnDestroy`），**禁** `FindGameObjectsWithTag`。列表次序就是 Awake 次序、跨运行不稳定，平局裁决必须自己按位置或 id 排。
- 分类倒排索引建在 `ActionController` 上（`SetAllActions` 里随"这个角色的那份表"一起重建），**每个角色都必须填 `CharacterObj.actionSubset`**（留空 = 全表，只准出现在没有第二家招式的工程里）：demo 的拳击行和移植的玩家行共用同一批 cancel tag 字面量（两边的连招都挂 `Punch2`），全表在场时优先级高的那一家会把另一家的连招抢走，而这种错在 Console 里一点痕迹都没有。开场 id 走 `CharacterObj.defaultActionId`，没填才退回 `GameMain` 里写死的那两个。用例里"用真表"的那几条同理要按家族取子集（`ActionFrameClockTests.FamilyOf`）。

## 性能验证

- 窗口按**逻辑帧**开（`LogicClock.Frame % 300`，5 秒一个窗）而不是渲染帧——`-nographics` 下两者差 80 多倍，按渲染帧开窗的话一个窗口只有几拍，稳态与头部增长混在一起看不出来。注意 `GC Allocated In Frame` 计数是**按渲染帧**清零的，探针若在同一个渲染帧里打印，那行的字符串拼接会被算进正在收尾的分区。每帧分配用 `GcProbe.cs` 的分区探针量，判据是**分区 0 B/帧**而不是整帧 0 B（调试 UI 的残留见 `Doc/issue/ui-inputtext-per-frame-alloc.md`）。
- 分配计数只认 `Unity.Profiling.ProfilerRecorder` 的 `ProfilerCategory.Memory / "GC Allocated In Frame"`；`Profiler.GetMonoUsedSizeLong()` 在编辑器里一帧之内不动，用它做差值会量到恒 0（Unity 2023.2 也已无 `GetAllocatedBytesForCurrentThread`）。
- 任何"全 0"的测量结论，必须自带一个已知非零的对照量（GcProbe 的自检是 1024 字节的分配）；对照量为 0 就说明量的是个瞎指标。详见 `Doc/bugfix/gc-probe-false-zero.md`。
- 0 B/帧的判据看**稳态**：常驻 List 的头几次扩容、某个静态类第一次被摸到时的构造（如 `PickActionMethod` 的字典与委托）都会记出一次性非零，别当回归去追。
