# HD-2D 世界约定：纵深走 Z，面向由逻辑决定

> 状态：已采纳 · 2026-10（第 5 条已修订 · 2026-10-13，见文末"修订"）

## 这条决定什么

移植后的世界里，三件事的约定固定下来：纵深走哪根轴、角色怎么转身、镜头用哪种。决定：**像素精灵贴在 3D 平面上（HD-2D），纵深走 Z，跳跃高度走 Y；面向的逻辑真源是 `inversed` 布尔，具体落地成什么变换交给表现层；镜头用正交（第 5 条是 2026-10-13 修订后的结论，原本写的是保持透视）。**

## 背景：两边轴不一样

- BeatEmUp：X 横向、**Y 纵深车道**。跳跃不改世界 Y 的"车道含义"——它把 `transform.position.y` 抬高让贴图飞起来，同时把 `CapsuleCollider2D.offset.y` 反向补偿下去，使碰撞体留在原车道上（`UnitActions.cs:288-292`）。纵深排序 `sortingOrder = y × -50`，且传的是车道值 `groundPos` 而不是实时 y，所以"飞的只是贴图"。
- 本工程：X 横向、**Y 高度**（重力积分与 `ProbeGround` 都在 Y 上）、Z 纵深。

## 决定与理由

1. **纵深 = Z，高度 = Y**（本工程的约定胜出，移植是轴的改名）。
   理由：本工程的 `CharacterObj.ProbeGround`（`CharacterObj.cs:237-256`）已经是"高度与车身分开"的正规实现——它向下做球体投射、起点取移动前后较高的脚底高度、探测距离不含半径，找到的地面高度直接写进 `to.y`。BeatEmUp 那套 collider-offset 补偿解决的是同一个问题（"跳跃时排序与命中车道不能乱"），但靠手工偏移维持；**不搬那个 hack**。纵深排序公式保留，只是按 Z 计算。
2. **面向的逻辑真源是 `inversed`，不是欧拉角**。
   理由：`ActionController.cs:389` 现在写死 `transform.eulerAngles = new Vector3(0, command.inversed ? 270 : 90, 0)`。这对 3D 模型正确，对精灵四边形错误——一张面向镜头的精灵绕 Y 转 90° 会侧对镜头，变成一条线。而镜像这件事在逻辑层本来就只用 `inversed` 布尔（输入镜像 `GetKeyInput`、位移符号 `NatureMove`、力向翻转 `GetForceDirection` 三处都是），所以只需要把"落地成什么变换"这一步交给表现层：模型走 Y 旋转，精灵走 `flipX`。
3. **纵深键不参与正反手镜像**。
   理由：`GetKeyInput` 只镜像 Forward↔Backward，因为"前/后"是相对角色朝向的；而"里/外"是屏幕空间概念，与角色朝哪边无关。这和 `Up/Duck` 本来就不镜像是同一个道理，属构造正确而非遗漏。
4. **竖轴语义从上段/下段改成纵深**。
   理由：本期素材（`Player.controller` 的 31 个状态）里没有蹲防、也没有上段招式，竖轴在 BeatEmUp 里的本来用途就是纵深。`KeyMap.Up/Duck` 保留（`TwinKick` 那种 `[2,3,6,101]` 指令结构不动，将来有素材还能用），2026-10-13 起它们真的有消费者了：表里的 `BoxingMoveFar`/`BoxingMoveNear` 就是被 `[8]`/`[2]` 触发的。
5. **镜头用正交**（修订后的结论，理由见文末"修订"），车道宽与可玩纵深由 `LevelBounds` 定，不由投影定。
   原条文是"保持透视，按 PPU 50 标定 FOV 与距离，使一个世界单位对应 50 像素"，并自己留了口子："如果对拍结论是必须回正交，只有相机要换"。第 1、2、3 条与时基、镜像有关，与投影方式无关，**一条没动**。

## 影响

- 世界从"1D 玩法线"变成"X+Z 的浅纵深车道"，`NatureMove` 要加 Z 位移、`RootMotionMethod.GoStraight` 要加可选的纵深参数、同轨角色要 pairwise 推挤。
- 面向抽象之后，`Assets/Scripts/AGENTS.md` 里"表现层不许把面向写死成欧拉角"要立成规则。
- 背景视差层（BeatEmUp 的 `ParalaxScrolling` 是按相机位移 × 系数改写 position）从 2D 层重排到 3D 空间，属 Step 2。

## 修订：镜头从透视改成 orthographic · 2026-10-13

起因：八向移动做完之后，"看得出角色换了车道"这件事完全依赖屏幕上那点位移。透视把纵深位移同时做成"缩小 + 上移"，而判定是在世界空间按 x/z 算的——两套东西一旦不单调对应，就会出现"看着没碰到却打到了"。

三条理由（按重要性）：

1. **同轨可读**。正交下 1 米车道位移在任何车道上都是同样的屏幕位移（屏幕位移 = 世界位移 × sin(pitch)），"两个角色对齐了没有"在画面上是单调的；透视下远车道的角色会缩小，眼睛的判据随车道变化。
2. **像素精灵的前置条件**。`PixelPerfectCamera`（`com.unity.2d.pixel-perfect`）只对正交有意义，而移植的素材就是 PPU 50 的逐帧 PNG（切片 1.7）。原条文留的那个口子就是为它留的。
3. **`depthSpeedRate` 的旧理由消失**。这个 0.8 原本写着"纵深位移被透视压缩过，1:1 会显得比横向快"。正交下没有透视可补偿，它退回成纯手感系数（原版也是把输入的 y 乘 0.8，值不动），斜向归一化用的还是它，所以八向等速关系不受影响。

改的三个数（`Assets/Scenes/GameMain.unity` 的 Main Camera + `GameMain.LateUpdate` 里的 base 常量）：

| 项 | 透视 | 正交 |
| :--- | :--- | :--- |
| 投影 | 透视，`fieldOfView 69.1` | `orthographic`，`size 2.5` |
| pitch | 10° | 25° |
| base 偏移 | (2, 2.4, -4) | (2, 2.75, -4) |

怎么算的（要动镜头就重算这三条）：

- `size` 决定垂直可视世界高度 = 2×size。角色 1.7 米，要它占画面高度 34%（等于原来那台透视相机的观感）⇒ size ≈ 1.7 / (2 × 0.34) = 2.5。
- `pitch` 决定"1 米车道位移有多少屏幕位移"= sin(pitch)。10° 只有 0.174：斜穿整个 3 米车道带才挪 0.52 单位，占 5 单位画面高的 10%，几乎读不出来。25° 是 0.423，同样的 3 米挪 1.27 单位 = 25% 画面高。
- `base.y` 与 pitch 是绑死的：脚下在画面里的竖直位置 = `-base.y × cos(pitch) + (角色z - base.z) × sin(pitch)`。pitch 抬到 25° 之后要维持脚下还在 -0.8 那一档（1.7 米的身子带点头部余量落在 ±2.5 内），base.y 就得从 2.4 抬到 2.75。

要在校准里眼睛过的就是 size 与 pitch 这两个数。**相机仍然不跟 z**：正交下可见纵深带 ≈ 2×size / sin(pitch) = 11.8 米，远宽于 3 米的车道带，所以 `LevelBounds` 的 z = ±1.5 从此是玩法决定（约 5 条车道，车道宽 = 两个 `laneRadius` = 0.6 米），不再受镜头约束——原来"近侧只剩 1.56 米余量"那套随透视一起作废。

切片 1.7 做像素对拍时会重写这个 size：`PixelPerfectCamera` 按参考分辨率自己算 `orthographicSize`，2.5 只是现在这套 3D 占位素材时期的值。
